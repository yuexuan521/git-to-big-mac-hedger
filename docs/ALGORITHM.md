# 算法说明

> 本文给出评分模型、等级映射与套餐匹配的形式化定义、参数标定过程与敏感性实验。
> 所有数字都可以用文末命令复现。

## 1. 问题定义

给定：

- 时间窗内的提交集合 $C = \{c_1, \dots, c_n\}$，每个提交带 `insertions`、`deletions`、`date`、`message`
- 门店商品目录 $M$（含价格、原价、热量）
- 档位表 $L_1..L_4$

求解三步映射：

```
s = f(C)                   ① 工作量评分
ℓ = level(s)               ② 等级判定
B = cap(ℓ)                 ③ 热量预算
x* = argmax_{x ∈ X(B)} U(x) ④ 套餐选择，X(B) = {x : kcal(x) ≤ B}
```

## 2. 评分模型

```
f(C) = 1.0 · A + 1.5 · D + 30 · |C|
```

其中 $A$ 为新增行数，$D$ 为删除行数，$|C|$ 为提交次数。实现见 `src/effort-scorer.js`。

**为什么删除权重更高。** 删除 1 行记 1.5 分，新增 1 行记 1.0 分。等权会奖励"堆代码"，而重构、删祖传代码、拆耦合的认知负荷显著高于同量新增——删掉 500 行历史包袱的人，理应比新增 500 行脚手架的人多吃一点。

**为什么提交权重是 30。** 这是全项目唯一一处偏离规范建议值（50）的参数，理由是**档位可达性**。设某天只改了一个 typo、提交 2 次：

```
s = A + 1.5D + 30 × 2
```

即使 $A=D=18$ 这种极小改动，$s = 18 + 6 + 60 = 84 < 100$，稳稳落在 L1。若权重取 50，同样情形 $s = 124$，直接进 L2——L1 就退化成了"0~1 次提交"的极端情形，而"今天只改了个 typo 正常下班"正是 L1 存在的唯一理由。

临界点可以精确算出：对 L1 演示场景（18 增 / 4 删 / 2 提交），

```
s(cw) = 18 + 1.5×4 + 2·cw = 24 + 2·cw
s(cw) ≥ 100  ⟺  cw ≥ 38
```

即提交权重超过 38 就会把该场景推入 L2。取 30 保留了 8 的余量。

### 2.1 提交权重敏感性（实测）

| 提交权重 | L1 场景 | L2 场景 | L3 场景 | L4 场景 |
| ---: | --- | --- | --- | --- |
| 20 | 64 / L1 | 320 / L2 | 790 / L3 | 1440 / L4 |
| **30（采用）** | **84 / L1** | **360 / L2** | **860 / L3** | **1570 / L4** |
| 40 | 104 / **L2** | 400 / L2 | 930 / L3 | 1700 / L4 |
| 50 | 124 / **L2** | 440 / L2 | 1000 / L3 | 1830 / L4 |

只有 L1 场景对权重敏感，且敏感点恰好落在 38——这与上式的解析结果一致。L2~L4 在 20~50 区间内保持稳定，说明权重选择没有"为了凑结果而调参"。

### 2.2 删除权重敏感性（实测，提交权重固定 30）

| 删除权重 | L1 | L2 | L3 | L4 |
| ---: | ---: | ---: | ---: | ---: |
| 1.0 | 82 | 340 | 770 | 1410 |
| **1.5（采用）** | **84** | **360** | **860** | **1570** |
| 2.0 | 86 | 380 | 950 | 1730 |
| 2.5 | 88 | 400 | 1040 | 1890 |

演示场景的删除量占比不高，因此该权重不影响档位判定；它影响的是**重构型工作日**——删除占比越高，得分抬升越明显。

## 3. 等级映射

```
L1 微光轻步   [0, 100)      cap = 400
L2 踏实前行   [100, 500)    cap = 700
L3 破浪攻坚   [500, 1200)   cap = 1100
L4 拯救世界   [1200, +∞)    cap = 2000（--unlimited 时为 ∞）
```

区间左闭右开，`resolveLevel` 取满足 $s \ge t_k$ 的最大 $k$。额度是**固定档位值**，不做档内插值：账单要说人话，"你落在 L3，上限 1100"比一条分段函数更容易解释，也更容易被质疑时站住。

## 4. 候选生成

设目录中热量可核算的商品集合为 $M_{ok} = \{m : kcal(m) \ne \text{null}\}$（当前 29 个，另有 20 个因名称无法对齐而被排除）。

候选集 $X(B)$ 由两部分组成：

1. **单份候选**：$m \in M_{ok}$ 且 $kcal(m) \le B$
2. **多份候选**：对每个满足 $kind = combo$ 且 $discountRate > 0$ 的商品 $m$，令
   ```
   kcal(k·m) = k · kcal(m)
   price(k·m) = k · price(m)
   ```
   仅当 $kcal(k·m) \le B$ 时纳入，当前 $k \in \{2\}$。

**为什么只让套餐叠加。** 单品叠加没有优惠故事（两个汉堡就是两个汉堡），而套餐的折扣率在放大后保持不变，可以真实地"用满额度"。

**为什么需要多份。** 门店在售最顶套餐为 949 kcal，L4 的 2000 额度单份永远用不满——按单份匹配，L4 的利用率上限只有 47%，会退化成"拯救世界的一天推荐你吃一份套餐"。加入 ×2 后，L4 的利用率从 47% 提升到 92%。

## 5. 目标函数

对每个候选 $x$：

```
d(x) = (originalPrice(x) − price(x)) / originalPrice(x)     折扣力度
v(x) = kcal(x) / price(x)                                   性价比（kcal/元）
u(x) = kcal(x) / B                                          额度利用率

U(x) = 0.40 · d(x) + 0.35 · v(x)/max_{y∈X(B)} v(y) + 0.25 · min(u(x), 1)
```

三点说明：

- $v$ 按候选集内最大值归一，避免跨档位量纲漂移（L1 的候选集与 L4 的候选集价格分布完全不同）。
- $u$ 截断到 1，否则 `--unlimited`（$B = \infty$）时该项无定义；此时以 2000 kcal 作为参考基线。
- 展示用的「综合评分」是 $100 \cdot U(x)$，因此账单里看到的是 0~100 的量纲。

**三个权重分别防什么。** 纯按 $d$ 排序会退化成"买最便宜的打折品"（L4 被推荐 9.9 元冰美式）；纯按 $u$ 排序会推荐最贵的；纯按 $v$ 排序会推荐热量密度最高的，容易撞上预算上限附近但毫无优惠的商品。三者共存才同时满足"省钱、够吃、用满额度"。

### 5.1 匹配权重敏感性（实测）

对四组权重分别重算 top-1：

| 权重方案 (d / v / u) | L1 | L2 | L3 | L4 |
| --- | --- | --- | --- | --- |
| **0.40 / 0.35 / 0.25（采用）** | 那么大鸡排 385 | 麦乐鸡中套餐 649 | 麦辣鸡腿三件套 921 | 麦辣鸡腿三件套 ×2 1842 |
| 0.60 / 0.20 / 0.20（折扣优先） | 同上 | 同上 | 同上 | 同上 |
| 0.20 / 0.55 / 0.25（性价比优先） | 同上 | 同上 | 同上 | 同上 |
| 0.33 / 0.34 / 0.33（均等） | 同上 | 同上 | 同上 | 同上 |

**结论要谨慎表述**：在当前数据集上，四组权重给出完全相同的 top-1，说明结论对权重扰动是稳健的——推荐不是调参调出来的。但反过来看，这也说明当前数据**无法区分**这三种偏好，因此不能宣称"0.40/0.35/0.25 是最优权重"。这是一个真实局限，见 §8。

## 6. 选择与并列处理

1. 按 $U$ 降序排序（`Array.prototype.sort` 稳定，同分时保留目录顺序）
2. `primary = scored[0]`，`alternates = scored[1..3]`
3. **差一点点**：在超预算候选中取 $kcal \le 1.15B$ 的子集，按超出量升序、折扣降序取首个。它不参与推荐，只用于告诉用户"再近一点就够得着"。

极端情况下 $X(B) = \emptyset$：返回 `primary = null`，账单输出「暂无合规套餐」，但等级、得分、额度照常打印——**降级而不是崩溃**。

## 7. 复杂度

| 阶段 | 时间 | 空间 |
| --- | --- | --- |
| Git 解析 | $O(n)$，$n$ 为提交数（上限 500） | $O(n)$ |
| 评分 | $O(n)$ | $O(1)$ |
| 目录构建 | $O(m)$，$m = 49$ | $O(m)$ |
| 候选生成 | $O(m)$，候选 ≤ 34 | $O(m)$ |
| 排序 | $O(c \log c)$，$c \le 34$ | $O(c)$ |

整体 $O(n + c \log c)$，实测端到端 < 100 ms（含 Node 启动）。

## 8. 已知局限

1. **只衡量变更量，不衡量难度。** 100 行 YAML 与 100 行无锁并发代码同分。这是行数代理指标的天花板，也是本模型最大的效度威胁。
2. **匹配是单目标贪心，不是组合优化。** 候选集只有 34 个，理论上可以用 0/1 背包求出"总价最低且热量达标"的精确解；但多品组合会让账单难以解释（"为什么是汉堡 + 两块鸡翅 + 一个派"），当前选择了解释性优先。
3. **同款叠加只到 ×2。** $k$ 的上界是经验值，不是从数据推出的。
4. **不建模用户偏好。** 过敏原、口味、是否吃过都不在目标函数里。
5. **快照有时效。** 价格与供应状态以 `capturedAt` 为准，过期快照不会自动失效。
6. **单人单仓库。** 没有跨仓库聚合，也不处理多人协作的贡献切分。
