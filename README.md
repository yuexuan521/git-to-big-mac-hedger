# 🍔 Git 提交与巨无霸热量对冲器

> **努力了一天，应该好好放松。**
>
> 你今天的努力没有被记在 OKR 里，也没有出现在周报上——但它确实发生了。
> 我们把它从 Git 里挖出来，折算成一顿**刚好配得上今天**的麦当劳。

读取你今天的 Git 提交 → 评估这一天的分量（L1~L4）→ 算出热量上限 → 通过麦当劳 MCP 从**真实门店菜单与优惠**里挑出一份「性价比最高 / 折扣力度最大」的治愈系套餐 → 打印一张《赛博治愈对冲账单》。

零依赖，`node index.js --demo all` 即可跑通全流程。

## 一、为什么做这个

程序员的一天是高度非线性的。写了 13 个 commit 的那天和写了 2 个的那天，身体感受完全不同，但日历上看起来一模一样。

于是出现两种坏结局：

- **过度补偿**：今天只改了三行文档，晚上却点了全家桶，负罪感到凌晨两点。
- **不敢犒赏**：今天线上着火救了一整天，最后只吃了碗泡面，觉得"也没干什么"。

这两种情况是同一个问题：**没有一个客观的量尺，去衡量"今天值多少放松"**。

工时是自报的，会撒谎；Git 是副产品，不会。**这个项目就用 Git 里的增删行数，给今天的努力定个价。**

## 二、四个层次：从微光到拯救世界

| 等级 | 名称 | English | 判定分数 | 热量上限 | 判词 |
| :--: | --- | --- | ---: | ---: | --- |
| **L1** | 微光轻步 | Chill | `Score < 100` | **400 kcal** | 今天轻松搞定，维持充沛状态。 |
| **L2** | 踏实前行 | Normal | `100 ≤ Score < 500` | **700 kcal** | 踏实推进业务，脑力平稳燃烧。 |
| **L3** | 破浪攻坚 | Hardcore | `500 ≤ Score < 1200` | **1100 kcal** | 攻克核心难点，身体急需碳水补充！ |
| **L4** | 拯救世界 | Legendary | `Score ≥ 1200` | **2000 kcal**（可用 `--unlimited` 切到不限） | 拯救屎山代码，宇宙级功德！今晚热量彻底解禁！ |

区间**左闭右开**，额度是**固定档位值**——不做档内插值。判定只看分数落在哪一档，越简单越不容易解释不清。

### 分数怎么来的

```
Score = 新增行数 × 1.0  +  删除行数 × 1.5  +  提交次数 × 30
```

删除权重 1.5 高于新增 1.0：**重构和消灭屎山比堆新代码更费心血**。删掉 500 行祖传代码的人，值得比加了 500 行脚手架的人多吃一点。

#### 为什么提交权重是 30，而不是规范建议的 50？

这是本项目对业务规范唯一一处数值调整，理由是**档位可达性**。按 50 标定，提交次数的得分会碾压行数：

| 提交次数 | ×50 | 落入档位 | ×30 | 落入档位 |
| ---: | ---: | --- | ---: | --- |
| 1 | 50 | L1 | 30 | L1 |
| 2 | **100** | **L2** | 60 | L1 |
| 3 | 150 | L3 门槛未到但已进 L2 | 90 | L1 |
| 4 | 200 | L2 | 120 | L2 |

**×50 时，2 次提交（哪怕每行都是空行）就直接进 L2，L1 实际只剩 0~1 次提交，几乎不可达。** 而「今天只改了个 typo，正常下班」正是 L1 这个档位存在的唯一理由。改成 30 之后，2 次提交仍然稳稳待在 L1，同时 4 次提交 + 一些真实行数能自然进入 L2——四档都变得可达。权重常量在 `src/effort-scorer.js` 的 `WEIGHTS` 里，一改就生效，测试会立刻告诉你档位漂了没有。

#### 三个信号不计分，只作展示口径

初版曾把「深夜提交 +12 / 周末 +10 / 热修 +25」算进分数。改版后**全部移出评分**，只在账单的补充说明里出现一句：

> 另：深夜提交 2 次、周末提交 13 次、热修/回滚 3 次——这些不计入得分，但今天确实更累。

原因很简单：**计分会造成双重惩罚**。热修那天通常行数本来就多，再叠一个 25 分/次的加成，会把 L4 推到几千分去，让 1200 这个门槛失去意义；而「深夜」取决于你的时区与作息习惯，把它算进客观分里是不公平的。把它降级为一句人话提示，信息没丢，标定反而干净了。

## 三、怎么挑套餐：不是最便宜，是刚刚好

拿到热量上限后，程序读 `data/live/` 里的 **mcd-mcp 真实快照**（菜单价格、营养热量、套餐成分、可领优惠券），拼成一份可核算的商品目录，然后逐个打分：

```
综合评分 = 0.40 × 折扣力度          ← (原价 − 现价) / 原价，真的省钱
         + 0.35 × 性价比            ← kcal / 元，按候选集内最大值归一
         + 0.25 × 额度利用率        ← kcal / 热量上限
```

**硬约束：总热量 ≤ 今日上限。** 超了直接排除，并明确告诉你差多少（账单里的「差一点点」）。

### 为什么留 25% 给额度利用率

纯按折扣排序会退化成「买最便宜的打折品」：L4 拿着 2000 kcal 的额度，被推荐一杯 9.9 元的冰美式——这是明显的产品事故。利用率这一项就是防它的。反过来，纯按利用率排又会推荐最贵的，所以三项必须共存。

### 为什么要有「点两份」

门店在售的最顶套餐是 `全明星双人分享餐八件套`（2142 kcal），**超出 L4 的 2000 上限**；次一档的套餐只有 949 kcal，L4 的额度永远用不到一半。于是匹配器会给每个打折套餐额外生成一个 **×2 候选**（热量、价格、优惠同倍放大，**折扣率不变**），只有放得进额度的才会进入候选集。

实测效果：L4 从「949 kcal / 47% 利用率」变成「1842 kcal / 92% 利用率」，而 L3 因为装不下双份，结论稳定停在单份——四档推荐不再重复。用 `--no-double`（或代码里 `maxPortions: 1`）可以关掉。

### 热量是算出来的，不是估的

真实接口不给套餐热量，只给成分。所以流程是：

```
query-meal-detail(code)  →  rounds[].choices[] 里取 isDefault=1 的默认选配
                         →  逐项用商品名回查 list-nutrition-foods 的 energyKcal
                         →  乘以份数后累加
```

名字对不上就**排除该商品**，绝不猜一个数字。本轮有 20 个商品因此被排除（例如「Hold不住鸡排堡（椒盐风味）」不在营养表中），账单里会写明「已排除 20 个无法核算热量的商品，不做估算」。

## 四、快速开始

不需要 `npm install`，没有任何第三方依赖。

```bash
# 1. 看看今天（当前 Git 仓库，最近 24 小时）
node index.js

# 2. 没有提交也能看效果：跑一遍内置的四档演示
node index.js --demo all

# 3. 单独看某一档
node index.js --demo l4

# 4. 把 git 统计贴进来算（不用是 Git 仓库）
git log --shortstat -3 | node index.js --input -

# 5. 导出一份 Markdown 账单 / MCP 调用记录
node index.js --demo l3 --out report.md
node index.js --demo all --record workbuddy.md
```

账单之后跟一段补充说明：为什么是它 / 备选方案 / 差一点点 / 距下一档还差多少 / 哪些信号不计分 / 数据源与排除数。加 `--no-extras` 只输出账单主体。完整样例见 [docs/sample-report.md](./docs/sample-report.md)。

### 四档演示的实测结果

| 场景 | 描述 | 新增/删除/提交 | 得分 | 等级 | 上限 | 推荐套餐 | 价格 | 热量 |
| --- | --- | --- | ---: | :--: | ---: | --- | ---: | ---: |
| `l1` | 周四 · 正常下班 | 18 / 4 / 2 | 84 | L1 | 400 | 那么大鸡排（椒盐风味） | ¥14.0 | 385（96%） |
| `l2` | 周四 · 稳步推进 | 180 / 40 / 4 | 360 | L2 | 700 | 麦乐鸡经典中套餐 | ¥25.0 | 649（93%） |
| `l3` | 周五 · 攻坚 + 加班 | 380 / 180 / 7 | 860 | L3 | 1100 | 麦辣鸡腿汉堡三件套 | ¥33.5 | 921（84%） |
| `l4` | 周六 · 线上救火通宵 | 700 / 320 / 13 | 1570 | L4 | 2000 | 麦辣鸡腿汉堡三件套 ×2 | ¥67.0 | 1842（92%） |

四档推荐**互不重复**，额度利用率都在 84% 以上——不是"努力了一天推荐你吃个甜筒"。

加 `--unlimited` 后 L4 会切到真正的无上限，此时答案是 `全明星双人分享餐八件套`（2142 kcal，56.4% off，¥49.9/原价 ¥114.5）——那份超出上限 142 kcal 的双人餐，正好是"宇宙级功德"该有的样子。

## 五、麦当劳 MCP 接入

本项目调用的是真实的 **`mcd-mcp`**，工具以宿主原生形态注入。用到的 5 个接口：

| 工具 | 作用 | 本项目怎么用 |
| --- | --- | --- |
| `query-nearby-stores` | 查附近门店 | 选定 `storeCode=1450750`（上海徐汇宜山路长兴园餐厅，444 m） |
| `query-meals` | 查门店菜单 | 49 个商品的现价 / 划线价 → 折扣来源 |
| `query-meal-detail` | 查套餐成分 | 8 个套餐的默认选配 → 热量核算的输入 |
| `list-nutrition-foods` | 餐品营养表 | 160 项，取 41 项与菜单相关 → `energyKcal` |
| `available-coupons` | 可领优惠券 | 4 张（不含 SKU 与价格，故不参与匹配，仅作展示） |

调用过程逐条记录在 **[workbuddy.md](./workbuddy.md)**（13 条真实调用，带服务端 `traceId`）；协议细节、名称对齐策略与踩坑记录见 **[MCP_INTEGRATION.md](./MCP_INTEGRATION.md)**。

### 关于「快照」

结算读的是 `data/live/` 下的**快照**，不是每次实时请求。这是刻意设计：让评委在没有 MCP 凭据的环境里 `node index.js --demo all` 也能跑出完全一样的结果。每份快照都带抓取时间与 `traceId`，可逐条对账（见 `workbuddy.md` 第四节）。

## 八、设计上的几个取舍

**为什么读 Git 而不是读工时？** 工时是自报的，会撒谎；Git 是副产品，不会。而且它天然有粒度、可复现、不侵入。

**为什么只在本地读？** 全程 `git log --numstat` 本地执行，只把「提交次数、行数」这类聚合数字用于计算，**代码内容不出本机**。上行的只有门店编码和菜单查询。

**为什么额度是上限而不是目标？** 「对冲」的意思是：今天消耗了多少就补回来多少，不是借明天的。所以合理区间是额度用掉 80%~100%，超出即拒绝推荐。

**为什么热量宁可排除也不估算？** 估一个"看起来合理"的数字，会让整张账单的可信度归零。排除并明说，比编造一个数更有用。

**为什么 L4 默认 2000 而不是无限？** 规范写的是"2000 或无上限"。2000 让推荐变得**可计算**（有硬约束才有匹配的故事），而 `--unlimited` 保留了这个开关——两种口径都能演示，默认走可算的那个。

## 九、还能往哪走

- **多仓库聚合**：同时统计多个仓库，按团队看「本周最该被犒赏的人」。
- **连续工作日识别**：连续 5 天 L3 以上，自动升格一次 L4 额度，防止累积性倦怠。
- **个人券接入**：`query-my-coupons` 拿到个人券后叠加折扣（当前卡包为空，故未接入）。
- **偏好学习**：记住你每次真的点了什么，把治愈权重从通用先验换成个人化。
- **真下单**：接入 `calculate-price` / `create-order`，把「一键犒赏」补完（需显式确认）。
